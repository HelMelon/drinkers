# Архитектура

## Поток запроса

```
браузер (Vue 3 SPA)
   │  fetch  {proto}://{host}:4000/api/...
   ▼
backend/app.js  ── express, CORS по списку origin, лимит входа
   │
   ├── search.js      → SQL: фильтр + поиск + LIMIT/OFFSET  ─┐
   ├── normalize.js   → валидация строки перед записью        │
   ├── import-plan.js → проверка всех строк, потом запись     ├──► PostgreSQL
   ├── export.js      → CSV/JSON                              │
   └── auth.js        → HMAC-токен, requireAuth               ─┘
```

`app.js` создаёт приложение и экспортирует его; `server.js` только слушает порт.
Это разделение нужно тестам: интеграционные тесты поднимают `app.listen(0)` на
свободном порту и ходят в него обычным `fetch`.

## Модель данных

Две таблицы, обе создаются `backend/schema.sql` (идемпотентно, через `npm run db:init`).

### `cocktails`

| Поле | Тип | Зачем так |
|---|---|---|
| `id` | `text` PK | исторические id вида `k83cokknmw` из исходных данных; новые генерируются |
| `name` | `text NOT NULL` | — |
| `composition` | `text` | состав одной строкой — по ней ищет фильтр ингредиентов |
| `volume` | `integer > 0` | мл; по нему работает фильтр объёма |
| `price` | `integer[]` | **массив**: домашняя цена и импортная. В исходных данных так и было |
| `iba_category` | `text` | `Classics` / `Unforgettables` / `New Era` / `Not categorized` |

Индексы: по `iba_category` и по `lower(name)`.

### `filters`

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `text` PK | читаемые слаги: `cat-classics`, `ing-gin`, `vol-big` |
| `kind` | `category` \| `ingredient` \| `volume` | как сопоставлять |
| `label` | `text` | подпись на кнопке |
| `match_value` | `text` | значение для `category` (равенство) и `ingredient` (подстрока) |
| `threshold` | `integer` | порог для `volume` |
| `sort_order` | `integer` | порядок кнопок |

Фильтры **не в коде, а в базе** — чтобы добавлять и переименовывать их без деплоя.

## Контракт API

| Метод | Путь | Доступ | Что делает |
|---|---|---|---|
| `POST` | `/api/login` | — | пароль → `{token}`; 5 попыток / 15 мин на IP |
| `GET` | `/api/cocktails` | — | все записи (до 500), по категории и имени — используется админкой |
| `GET` | `/api/cocktails/search` | — | `filter, q, page, per_page, sort` → `{items, total, page, per_page, pages}` |
| `GET` | `/api/cocktails/random` | — | случайный коктейль в рамках `filter` |
| `GET` | `/api/cocktails/:id` | — | одна запись или `404` |
| `POST` | `/api/cocktails` | токен | создание (upsert по id) |
| `PATCH` | `/api/cocktails/:id` | токен | частичное обновление |
| `DELETE` | `/api/cocktails/:id` | токен | удаление |
| `GET` | `/api/filters` | — | фильтры + `count` совпадений |
| `POST/PATCH/DELETE` | `/api/filters/:id` | токен | управление фильтрами |
| `POST` | `/api/import` | токен | `{format, mode, content}` → отчёт `{total, added, updated, skipped, errors}` |
| `GET` | `/api/export?format=csv\|json` | токен | скачивание всей базы |
| `GET` | `/api/stats` | — | сводка: сколько коктейлей, фильтров, распределение по категориям |

Ошибки всегда в одном формате: `{status: '400', statusText: 'текст'}`. Для 5xx текст
общий — детали уходят только в лог (`http-error.js`).

## Ключевые решения и почему именно так

**Фильтры в базе, а не в коде.** Изначально пять фильтров были захардкожены в
компонентах. Это значит: новый ингредиент — это правка кода и деплой. Перенос в
таблицу `filters` дал возможность управлять каталогом из админки и убрал дублирование
логики между клиентом и сервером.

**Фильтрация на сервере, а не в браузере.** Первая версия тянула все 47 записей и
фильтровала в памяти. Пока записей мало, это работает, но: (а) фильтр и пагинация
начинали дублироваться, (б) клиент не мог показать «сколько всего». Теперь в SQL
считается и выборка, и `total`, и счётчики фильтров.

**Двухфазный импорт.** Первая версия в режиме `replace` делала `DELETE`, а потом
построчно вставляла — битая строка в середине оставляла каталог полупустым. Теперь
сначала проверяются все строки (`import-plan.js`), и только потом идёт запись в
транзакции. Для `replace` любая ошибка — отказ целиком.

**Пароль → HMAC-токен без библиотек.** Для одного админа JWT-стек избыточен:
`crypto.createHmac` + `timingSafeEqual` дают подпись и сравнение без зависимостей.
Ограничение: токен нельзя отозвать досрочно (живёт 12 часов), «Выйти» чистит только
`localStorage`.

**Цена — массив.** В исходных данных у коктейля две цены (домашняя и импортная), у
двух записей было по три — такие обрезаны до двух (см. аудит). Массив честнее, чем
две колонки: количество цен исторически переменное.

**Лимит попыток в памяти процесса.** Достаточно для одного инстанса и не требует
Redis. Минус: рестарт обнуляет счётчик, при нескольких инстансах нужен общий стор.

**CSV-экспорт с BOM.** Excel на русской Windows без BOM читает UTF-8 как cp1251 и
ломает кириллицу. BOM решает это ценой трёх байт; JSON отдаётся без BOM, чтобы не
ломать строгие парсеры.

## Тесты

| Уровень | Сколько | Что покрывает |
|---|---|---|
| Юнит (бэкенд) | 29 | построение SQL, экранирование LIKE, пагинация, разбор CSV, план импорта, лимитер, формат ошибок, имя файла экспорта |
| Интеграционные (бэкенд) | 25 | реальные роуты на реальном Postgres: 401, CRUD, импорт/экспорт, поиск, random, CORS, сверка `count` фильтра с `total` |
| Фронтенд (vitest + jsdom) | 16 | каталог по страницам, фильтры и aria-pressed, состояния ошибки/пустоты, админка (вход, правка, вкладки, импорт файла) |

Фронтенд-тесты не зависят от живого API: данные — снимок в `frontend/tests/fixtures.json`,
поведение эндпоинтов эмулирует `frontend/tests/fakeApi.js`. Бэкенд-тесты поднимают
приложение на свободном порту и пересоздают базу перед каждым тестом.

## CI

`.github/workflows/ci.yml`, два джоба на каждый push/PR в `main`:

- `backend` — сервис `postgres:16` с healthcheck → `npm ci` → `db:init` → юнит → интеграционные;
- `frontend` — `npm ci` → `eslint` → тесты → `vite build`.

Кэш npm по lock-файлам, отмена устаревших прогонов через `concurrency`.
